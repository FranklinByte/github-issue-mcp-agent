# 产品需求文档

## 用户与问题

学生软件开发/课程项目团队和小型开源维护者需要整理Issue信息、分配标签和回复。报告常缺复现环境、预期/实际结果；维护者重复追问，同时不愿让模型直接改仓库。此判断是产品假设，不是已完成访谈的结论。

核心任务是“从现有Issue生成可检查的分诊建议，并让维护者决定是否执行”。分析与写入分离，审批对象是一份明确的参数快照，不是抽象的“是否允许Agent操作”。

## 为什么使用Agent

固定表单擅长收集标准字段，但无法覆盖已有自由文本Issue和变化的自然语言任务。模型可选择需要的仓库、评论、相关Issue上下文，再生成结构化建议。成本是误判、外部文本注入和模型费用，因此只给六个只读工具、最多四轮、失败立即停止。Offline规则/手动模式既是无Key演示路径，也是对照基线，不证明模型价值已经成立。

## 为什么使用MCP

MCP把工具发现、Schema、调用协议和业务权限边界从Agent实现中分离。Client可以发现Server能力，Server独立持有PAT；stdio与HTTP均可用同一业务工具。直接API仍然更简单，只有需要工具复用、清晰凭据隔离和多客户端接入时MCP的成本才合理，本项目选择它是为了演示这种边界，不是因为CRUD必须使用MCP。

## 范围

包含九个工具、自然语言/手动任务、结构化建议、持久化审批、审计、受控GitHubREST、离线Mock、有界Tool Calling、API、工作台和评测。

不包含代码/PR审查、代码生成、关闭/删除、仓库管理、成员权限、RAG、向量库、LangGraph、多Agent、Webhook自动写入、远程OAuth、多租户后台、自动处理不确定写入。

## 验收

1. 所有演示读取和批准后写入均通过官方MCP Client/Server边界。
2. 模型不能调用写工具，也不能批准动作；浏览器显示完整参数和仓库。
3. 未审批、参数变更、过期、拒绝、越权、重复请求均不会造成未授权POST。
4. 没有Key仍能本地运行，界面明确OFFLINE/MOCK，模型失效有降级标识。
5. 50条固定回归、分支覆盖率目标80%、Docker非root/health/重启验证、桌面手机检查有原始结果。

## 成功与失败

工程成功：权限判定一致，未经审批写入0，重复写入被抑制，失败可定位。产品成功待验证：用户能准确理解将发生的变更，愿意采用建议，完成任务用时较纯手工有改善。失败指标包括误批准、不能识别仓库/正文变化、建议失真、过高拒绝率、UNKNOWN难以处置和模型成本不成比例。

目前产品收益没有数据。下一步是3-5人小规模可用性测试，不以小样本估计总体市场需求或统计显著效率提升。
