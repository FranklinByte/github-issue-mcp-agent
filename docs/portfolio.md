# 项目介绍与简历材料

## 90秒介绍

我做了一个面向学生开发团队的GitHub Issue协作Agent，重点不是写代码，而是让外部工具调用可控、可审批、可追溯。它读取Issue、标签和评论，生成缺失信息、分类、标签和回复建议。模型只拿到从MCP动态发现的六个只读工具，最多四轮；标签、评论、创建Issue只能先生成提案。

用户看到完整仓库、工具参数和影响后逐项批准。审批令牌绑定会话、工具和完整参数指纹，五分钟有效、只能使用一次。Server独立校验Allowlist和Schema，SQLite用事务和唯一幂等指纹保证并发请求只有一个取得写入权。

比较难的部分是可靠写入：如果GitHub可能已写成功但响应超时，自动重试可能重复评论。因此我采用持久化占位、一次发送，不确定结果保留UNKNOWN或EXECUTING，由人核对，而不宣称跨网络exactly-once。

项目使用官方Python MCP SDK，真实跑通stdio和容器内Streamable HTTP，并验证旧初始化兼容路径。默认完全离线，固定50条AI辅助合成回归覆盖权限、审批、注入、重复执行和GitHub错误；Docker验证非root、健康和重启持久化。真实模型、真实GitHub业务请求和真实写入这次都没有执行，所以不会把Mock回归成绩说成模型准确率或生产效果。

## 简历技术版

**GitHub Issue协作Agent | Python / MCP / FastAPI / SQLite / Docker**

- 独立实现九个受限GitHub工具，使用官方MCP SDK完成动态Schema发现、stdio与本地Streamable HTTP调用；轻量Tool Calling循环限制四轮，写能力仅形成结构化提案。
- 实现Allowlist、严格参数校验、会话与参数指纹绑定的一次性审批；利用SQLite事务和唯一幂等记录抑制并发/重复写入，并对不确定结果停止自动重试。
- 构建50条AI-assisted synthetic regression案例及JSON/CSV/Markdown报告，验证未经审批写入为0；测试、分支覆盖与Docker具体数值以冻结验证记录填写，不将离线结果表述为真实模型效果。

## 简历产品/解决方案版

**学生团队Issue协作工作台 | AI辅助分诊与受控执行**

- 将自由文本Issue整理、标签建议和回复草稿设计为“建议-完整预览-逐项审批-执行审计”流程，明确只读自动化与高影响写操作的权限分层。
- 对比Issue Forms、手工流程和官方GitHub MCP Server，选择九工具有界场景，提供无账号Mock演示、错误/限流/降级状态及可检查的执行记录。
- 交付PRD、用户画像假设、权限矩阵、指标口径和3-5人可用性测试计划；尚无真实访谈与效率提升数据，待用户测试验证产品价值。
